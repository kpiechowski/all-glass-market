# Settings belong to the module that uses them; there is no Settings module for now

V1 kept every setting in one generic key/value table behind a "Settings" screen: untyped strings, keys no code guarded, plaintext API credentials copied into the activity log, and 8 of its 15 keys never read by anything. V2 does not port it. A setting lives with the module or integration that consumes it, in the plainest home that works: a code constant for business rules (VAT belongs to Offers), `.env` read only through `config/` for deploy-time values and every secret (WooCommerce and WordPress credentials go to `config/services.php`), `Preferences` for per-user choices (ADR 0006), and data of the owning module when it is really business data.

This is not a ban. When the system needs values that non-developers must change without a deploy, the owning module adds them as code-defined, typed definitions written through a command, the same shape as Preferences, never as a free-form key/value table. A shared Settings module, or one admin screen gathering module-owned settings, is worth building when several such values exist, when they change more often than deploys, or when two or more modules need them on one screen. Secrets stay out of the database even then.
