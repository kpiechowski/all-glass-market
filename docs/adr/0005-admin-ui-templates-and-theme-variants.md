# Admin screens follow named templates; the theme styles Filament through variant classes

The first module built by agents had screens that technically worked but read badly: a grid of section boxes on an edit form, fields paired without meaning, tables with half-empty columns, and header actions in four competing colours. Abstract rules ("keep it clean") did not stop this, because an agent follows a concrete pattern far more reliably than a principle. So every screen starts from one of a small set of named templates (list, form, record view, settings, action modal, dashboard), each with a code skeleton. The rules live in the `admin-ui-design` skill, and their reasons live here, because an agent needs the rule to comply and a person needs the reason to change it.

One column of sections is the default because a form is read top to bottom. Two columns of boxes make the eye zig-zag and hide which part matters. A side column is kept for status and metadata, which are worth keeping in view. Colour marks states only, because a panel where every category is a saturated badge has no signal left for what needs attention. Dangerous actions sit in the "⋮" menu, so the most destructive button is never the loudest one on the page.

The theme styles native `fi-*` classes and a few named variant classes applied through `extraAttributes()`. Tailwind utilities are used only in our own Blade views. Utilities sprinkled onto schema components are what made the first theme impossible to reason about: nobody can see where a spacing came from or change it in one place. Overriding a published vendor view breaks on Filament upgrades, so it happens only on an explicit human decision, and each override is listed. The look itself is worked out on a local-only Styleguide page reviewed by a human, because an agent cannot judge visual quality and driving a Livewire panel in a browser is too slow to be worth it.
