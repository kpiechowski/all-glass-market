# Per-user preferences live in a small Preferences module, and every preference is defined in code

The dashboard "Szybki dostęp" widget is the first per-user setting, but not the last: an onboarding step, hidden table columns and default filters will follow. Putting them on the `users` table would make the identity aggregate the home of every UI setting, and putting a write path into Core would turn the contracts layer into a place with business data. So a small `Preferences` module owns one generic table (`user_id`, `key`, JSON `value`, unique per user and key).

A generic table with a free-form `SavePreference(key, value)` would fill up with keys and shapes nobody guards. Instead every preference is a class implementing a Core contract (`PreferenceDefinition`): its key, its default value, and the rule that validates and normalises a value. The handler resolves the definition by key and rejects an unknown key, so the rules for a preference sit in one place, and a new preference is a new class, not a migration. A user without a stored row gets the definition's default; there are no global or per-role rows for now, and a scope column can be added later without breaking the model.

Other modules never reach into Preferences. They read and write through its `UserPreferences` ModuleApi and register their own definitions through the Core contract, the same way modules feed the quick-access item registry, which also lives in Core. The registry stores and returns item keys only; URLs, icons and visibility are resolved from code at render time, so a URL never comes from user input and a renamed page does not break saved preferences. Preferences survive account deactivation, because accounts are not deleted; a cleanup listener comes only if Users gains hard deletion.

In the database `user_preferences.user_id` references `users` with a cascading delete. That is a storage-level integrity rule, not a domain relation: the Preferences domain holds only the user id and never loads a user.
